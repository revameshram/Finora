0. How to Use This Document
This is a living context-preservation doc for Finora, a multi-module personal finance suite. Its job is to hold everything gathered/decided so far in one place so nothing is lost between sessions. Content comes from three kinds of sources, and each module section below labels which is which:
Observed — directly seen in Westro (westro.in) screenshots or live page fetch. Reverse-engineered feature reference only — not a copy of their branding, code, or copy text.
Inferred — a reasonable guess based on names/tags/adjacent UI, explicitly not verified.
Finora decision — your own product/build requirement, independent of what Westro does (sometimes matching it, sometimes deliberately different).
Modules covered so far in full depth: Expense Tracker (§4), Net Worth Tracker (§5), Portfolio Tracker (§6), Goal Manager (§7), Trip Manager (§8, expanded across §12, §15.2, §16.1–16.5, §16.13–16.14), FIRE Planner (§11, resolved across §15.1, §16.6–16.7), and Vault (§13, resolved across §15.3, §16.8–16.10). Not yet covered: EMI Manager — entirely unexplored, still Coming Soon status in Westro itself (see §9, §17).
1. Project Identity
Name: Finora.
Nature: a multi-module personal finance suite — both a real personal tool and a placement-portfolio piece.
Stack (consistent across modules): Spring Boot 3.x + Spring Data JPA + PostgreSQL/Supabase backend; React 18 + TypeScript + Vite + Tailwind frontend; JWT-based auth.
Related prior projects feeding into this: Asset Hub (polymorphic asset architecture, XIRR/CAGR, live pricing via Yahoo Finance/AMFI/CoinGecko), WealthMap (Indian-family net worth tracker), KYCc (credit card/personal finance tracker).
Workflow convention: phased AI-IDE prompts, mandatory Step 0 written plan (with worked numeric examples) before any code, package namespacing by module (com.<app>.<module>.*), DB tables prefixed per module to avoid collisions.
1.1 Scope & Build Decisions — Confirmed
The following were explicitly decided by the person building Finora (not inferred), and supersede any earlier ‘open question’ framing on the same topics elsewhere in this doc:
Module scope: all 8 modules are in scope — Net Worth Tracker, Expense Tracker, Portfolio Tracker, Goal Manager, Trip Manager, FIRE Planner, Vault, EMI Manager. This doc should capture everything gathered so far in full detail, not a trimmed subset.
Build order: no fixed sequencing is baked into this document — all modules are documented flat, side by side. Sequencing is a separate, later decision, not something this reference doc needs to prescribe.
Suite-wide Insights tab (§2.5): adopt fully and build early — not deferred to a later phase, not simplified down to 1–2 charts. The cross-module aggregation dashboard (Financial Health Overview, Key Metrics by life-area, Trends charts, Recommendations feed) is a first-class, early-build feature for Finora.
Multi-profile / family sharing (§2.6): adopt fully — full multi-profile support with the cross-profile data-access sharing toggle, matching Westro’s Observed behavior (opt-in per profile, Recommended-on by default). Not simplified to siloed profiles, not deferred to single-profile-only.
Trip Manager AI itinerary planner: keep as a real, core AI feature (calling an external LLM API) — not a stretch/optional add-on to build after the rest of the module. Budget real implementation effort and API cost/latency planning for it accordingly.

2.3 Cross-Module Linking — Universal Pattern (Finora decision, confirmed by Observed evidence)
This is the single most important structural finding across all modules gathered so far: content is interlinked across modules, with an explicit, per-item option to delink or exclude. This is not one module's quirk — it shows up consistently and should be built as a shared mechanism, not reimplemented per module.
Two distinct mechanisms observed, easy to conflate — keep them separate: (1) a soft Include/Exclude toggle on any individual record (asset, liability, transaction) that keeps the data but drops it from totals/calculations; (2) a Delink action specific to cross-module-sourced records (e.g. a Net Worth asset pulled from Portfolio Tracker) that severs the live sync, likely converting it to a standalone manual record or removing it.
Confirmed instances: Net Worth Tracker liabilities have an enable/disable toggle in Actions; Net Worth Tracker assets sourced from Portfolio Tracker show a lock icon + Delink action, plus a section-level “Include Portfolio” checkbox and “Open Portfolio” shortcut; Expense Tracker transactions have an include/exclude toggle as well (confirmed this session).
Finora decision: build this as a shared backend concern — e.g. a generic isIncluded/isLinked + sourceModule + sourceRecordId pattern reusable across Asset, Liability, Transaction, and any future cross-module record, rather than bespoke flags per entity.
2.4 Other Universal Patterns (Finora decisions layered onto the Observed base)
Live price as purchase price: an opt-in checkbox on every “add holding/asset” form across the whole project (not just Portfolio Tracker) that pre-fills the cost field with the current live price instead of requiring manual entry.
Inline live-price display: wherever an add-item form has a price/cost field, show the current live price in small text nearby for reference, project-wide.
Currency toggle button: a simple button to flip displayed values between ₹ and $ using the live FX rate — generalized from the pattern seen on Portfolio Tracker's US Stocks tab.
Schedule detail modal: the FD amortization-schedule modal (opened via a hand/view icon in Actions) should be replicated for Bonds as well (Observed: FD has it; Bonds doesn't yet in Westro — Finora decision to add it).
Toast notifications: a reusable success/error toast component (Observed pattern: green “SUCCESS — ETF added.” top-right, dismissible) for any create/update/delete action across all modules.
Financial Insights block: Observed independently on both Net Worth Tracker and Expense Tracker — each module gets its own composite health score + component ratios + a Recommendations feed. Worth formalizing as a shared “Insights panel” UI pattern with per-module scoring logic underneath (see §4.4 and §5.4 for the two observed scoring models, which differ).
2.5 Suite-Wide Insights Tab — Observed (corrects an earlier assumption)
The Workspace screen has two top-level tabs — Tools (the module grid, §2.2) and Insights. Insights is a genuine cross-module aggregation dashboard, separate from and in addition to each module's own internal Insights/Financial Health panel (§2.4). This directly corrects an assumption made in the earlier Portfolio Tracker reference doc, which stated ‘no cross-module service calls for MVP — don't design for it now.’ Westro's actual architecture has a live suite-level aggregation layer; Finora should plan for one, even if it's deferred past an initial module-by-module MVP.
Suite-wide Financial Health Overview: a single 0–100 score with a qualitative badge (e.g. 85/100 “Excellent”), explicitly described as ‘Based on net worth, debt ratio, and liquidity.’ This is a third, distinct scoring layer alongside each module's own score (Net Worth Tracker and Expense Tracker each compute their own separately, per §4.4/§5.4) — three scoring layers total: per-module, and one suite-level composite.
Key Metrics grid, grouped by life-area, each card tagged with its source module(s): Financial foundation (Debt Service %); Cash flow and growth (Savings Rate); Travel planning (Upcoming Trips, Total Trip Spending, Avg per Trip — sourced from Trip Manager); Investments (Investments Match: Linked/Not-linked status, Portfolio Return); Goals and long-term plans (FIRE Progress, Spending vs FIRE Plan, Goal Progress).
Trends and Analysis charts, each tagged with source module(s): Net worth by category, Portfolio mix, Portfolio growth, Progress toward FIRE, Assets and debt, Trip spending, and Goal balances by category — the last one carries an explicit note: ‘goal-scoped; not added to net worth,’ confirming Goal Manager balances are deliberately excluded from Net Worth totals by default (avoids double-counting against linked Portfolio Tracker assets that may already be feeding a goal).
Insights and Recommendations feed: a suite-wide synthesis, distinct from and richer than any single module's own Recommendations feed — color-coded cards (green/orange/red), each citing its source module tag(s), e.g. ‘Portfolio is linked into Net Worth’ (Portfolio Tracker + Net Worth), ‘2 goals are behind schedule’ (Goal Manager), ‘High Per-Trip Spending’ (Trip Manager), ‘Low Liquidity,’ ‘Manageable Debt,’ ‘Well-Allocated Assets.’
Finora decision: confirmed in §1.1 — adopt fully and build early. Plan the data model with consistent source-module tagging on any record/metric that could feed the suite-wide view, since it's a first-class feature, not a deferred one.
2.6 Profile Management — Observed
Profile page is a carousel, not a static card: dot-indicator + next/prev navigation cycling through multiple info slides per profile (at least a stats-overview slide confirmed; other slide contents not yet captured).
Edit Profile modal — two tabs: Basics (Name, Email with a Verify action, Gender picker: Male/Female/Other, Date of Birth) and Data access (a cross-profile sharing toggle: ‘Allow cross-profile data access — Use this profile in other profiles’ tools,’ marked Recommended and on by default).
Create New Profile modal mirrors the same two-tab structure exactly — confirms Data access is a setting decided at profile-creation time, not bolted on later.
Finora decision: confirmed in §1.1 — build the full multi-profile model with a genuine cross-profile data-access permission toggle (opt-in per profile), matching Westro's Observed behavior exactly, not simplified to hard isolation between profiles.
3. Cross-Module Data Model Conventions (Finora decisions)
One shared User/Profile table at the umbrella-app level; each module's tables reference user_id/profileId as a FK but live under their own table prefix (e.g. nw_ for Net Worth, pt_ for Portfolio, et_ for Expense Tracker) so no collisions as modules are added.
Package namespace by module, not by layer: com.finora.<module>.* with controller/service/repository/model as sub-packages inside each module package.
JWT auth is module-agnostic — issuance lives outside any single module; each module only validates a JWT and reads user_id from claims.
No cross-module service calls assumed for early builds — each module should be functional standalone; a future cross-module aggregation layer (e.g. true all-module net worth) is a separate concern, not designed for yet but not blocked either.
Currency: store amounts in a single baseCurrency per user (default INR); convert for display only via a live rates API. Base vs. display currency is a workspace/profile-level setting, not per-module.
4. Module Deep Dive — Expense Tracker
Fully explored. Month-scoped budgeting ledger; the suite's primary cash-flow lens.
4.1 Core Concepts — Observed
Budget Month scoping: every record (income, transactions, tasks, notes) partitioned by month; nothing carries over automatically. “Copy From” bulk-duplicates income/transactions/tasks from a chosen source month.
Pending vs. Done state machine on every transaction — silently branches how summary metrics compute (see §4.3).
Include/Exclude toggle on individual transactions (confirmed this session) — same universal pattern as §2.3, lets a transaction be kept but dropped from totals without deleting it.
Combinable filters: status pills (All/Pending/Done) x category pills (Expense/EMI/Investment/Savings/Undecided/Retirement/FIRE/Unplanned Travel/Home Improvement/Other) — category-based transaction filtering confirmed on the dashboard.
4.2 Features — Observed
Income Sources — Name, Amount, optional Instrument; searchable/sortable; edit/delete/history actions.
Transactions — Item, Description, Category, Amount, Payment Status, Payment Date; inline Done/Pending toggle; include/exclude toggle; search + combined filters.
Goal Manager linking — optional, surfaced for Savings/Investment/Retirement/FIRE categories. Originally understood as ‘Done triggers a contribution’; corrected in §7.8 — Done tags/associates the transaction with the goal for reporting, but does not move the goal's Saved/progress figure. Only Goal Manager's own Funding (starting balance) and Link Investments (live Portfolio Tracker value) affect goal balance.
Tasks — Task, Status, optional due Date, Notes.
Notes — freeform, timestamped, append-only per month.
Summary tab — Category Breakdown donut + Transaction Status donut (Pending vs Done, amount + count).
4.3 Dashboard Metrics — Verified Formulas
Metric
Formula
Notes
Total Inflow
Σ Income.amount (this month)
Unaffected by transactions.
Total Outflow
Σ Transaction.amount WHERE status IN (Pending, Done)
Includes committed-but-unpaid spend.
Cash Flow
Total Inflow − Total Outflow
Forward-looking / committed view.
Net Position
Total Inflow − Σ Transaction.amount WHERE status = Done
Actual settled position; ignores Pending.
Pending
Σ Transaction.amount WHERE status = Pending
Standalone sum.
Verified against a captured state: ₹99,940 inflow (1 income row) + one Pending ₹1,999 Expense transaction produced Total Outflow ₹1,999, Cash Flow ₹97,941, Net Position ₹99,940 (unchanged), Pending ₹1,999.

5. Module Deep Dive — Net Worth Tracker
5.1 Core Concepts — Observed
Three-tab dashboard: Assets / Liabilities / Summary.
Assets can be Manual (fully editable) or Portfolio-linked (read-only, auto-synced, lock icon, per-row Delink action) — portfolio linking is live and working, not just a schema hook as originally assumed in the pre-screenshot reference doc.
Section-level “Include Portfolio” checkbox + “Open Portfolio” shortcut sits above the linked-assets list.
Liabilities carry a separate soft enable/disable toggle in Actions (distinct from Delink) — include/exclude from Net Worth totals without deleting.
5.2 Categories — Observed (broader than originally assumed)
Asset categories: Cash & Bank, Investments, Crypto, Gold & Silver, Real Estate, Vehicles, Retirement Accounts, Business Assets, and at least one more category cut off in the screenshot (likely Personal or Portfolio-related) — confirm before finalizing the enum.

Category Breakdown: Donut/Pie toggle, separate Assets-by-category and Liabilities-by-category panels with hover tooltips showing exact value + % of total.

7. Module Deep Dive — Goal Manager
Fully explored. Savings-goal tracker with pace tracking against a monthly capacity, optional live linking to Portfolio Tracker holdings, and bulk-contribution tooling.
7.1 Dashboard — Observed
Icon rail: Overview / Achievements / Timeline / History.
Header KPIs: Saved (₹ + % of target via radial gauge), On Track count, Behind count, Monthly (total required contribution rate across all goals), Next Due (days + goal name).

11.5 FIRE Math — Inferred (reconstructed from visible inputs/outputs; the calculation engine itself is not directly observable)
FIRE Number — Annual Expenses in Retirement ÷ (Safe Withdrawal Rate ÷ 100) — the standard 4%-rule inverse (e.g. a 4% SWR implies a 25×-expenses multiple), consistent with the sidebar subtext in §11.3.
Years to FIRE (Inferred) — solve for n such that the future value of (current corpus compounded at Expected Annual Return) plus (Monthly Savings as an annuity at the same rate) reaches an inflation-adjusted FIRE Number (Annual Expenses grown at Expected Annual Inflation, then divided by SWR) — the same compound-growth + FV-of-annuity shape already scoped for Net Worth Tracker’s projection engine (§5.5) and Portfolio Tracker’s Growth Outlook (§6.3); a strong reuse candidate.
Required Savings mode (Inferred, not screenshotted) — likely the inverse solve — given a target retirement age, back-calculate the Monthly Savings that closes the gap between the current corpus’s projected value and the inflation-adjusted FIRE Number by that age.

13.6 Finora-Specific Build Decisions for This Module
Genuine zero-knowledge design — never persist the vault master password, and never store note plaintext or a recoverable derivation of it server-side — mirrors Westro’s explicit ‘cannot open the notes’ / ‘not stored on our infrastructure’ claims; Finora should actually satisfy this, not just claim it in copy. Recovery is backup-codes-only, by design, with no server-side password reset path.
Backup codes — generate exactly 3 one-time, high-entropy codes at setup, shown once, never retrievable again — derive/wrap the note-encryption key from them rather than storing the codes themselves.
Device Protection and Biometric Unlock — both remain optional convenience layers on top of the master password, never a replacement for it — same relationship Westro describes (‘your password still works’).
Reuse shared components — the empty-state and onboarding-drawer components already scoped in §12.5 rather than building vault-specific versions.
Client-side-only search — query note labels/descriptions against decrypted-in-memory data on the client — never send plaintext search terms or note bodies to the backend.

Search scope (Finora decision, resolves §14’s question) — implement note search entirely client-side against decrypted-in-memory data. Never index note bodies or labels server-side, even in encrypted form — a server-side index (encrypted or not) creates a metadata/timing side-channel that Westro’s ‘cannot open the notes’ claim doesn’t need to accept, and Finora’s own zero-knowledge decision in §13.6 should hold to the stricter standard.
Disclaimer duplication (resolves the wording note in §13.5) — Finora decision: treat it as a Westro copy-editing artifact, not a deliberate double warning — Finora’s own disclaimer copy should state the ‘lock before stepping away’ guidance once, cleanly, rather than reproducing the duplication.
With §15, every item raised in §14 for FIRE Planner, Trip Manager, and Vault now has either a confirmed Observed answer (already in §11–§13) or an explicitly labeled Inferred/Finora-decision answer here — no open stubs remain for these three modules. Genuinely unscreenshotted UI (Plan/Money/Pack & Prep/Notes tab layouts, the Vault Settings screen, FIRE Planner’s Required Savings screen) should still be re-verified against the live site before implementation; the labels above indicate confidence level, not certainty.

16.12 Finora-Specific Build Decisions (this session)
Vault unlock bot-throttling — add a CAPTCHA (or equivalent, e.g. hidden honeypot + rate-limit escalation) on the vault-unlock endpoint specifically, separate from normal login throttling, matching the extra scrutiny Westro applies here (§16.9).
Timed secret reveal — implement Vault’s Secret Value reveal as a client-only countdown (no server round-trip needed to re-hide), defaulting to ~30s, mirroring §16.10.
Generalize dependent-linking beyond Trip Manager — the parentParticipantId self-reference pattern in §16.4 is a good candidate for the shared Profile/family-member model referenced in §2.6, rather than being Trip-Manager-specific.
Guard all percentage/ratio displays against N/0 — the observed “NaN%” bug on an unset trip budget (§16.2) is a concrete reminder to null-guard every %-utilization display suite-wide (Budget vs Plan, Portfolio, Net Worth, FIRE Planner) rather than only where it was directly observed.
